# OntoFlow v1.4.2 — 复杂业务读取、来源身份及语义状态修复

基于已公开的 v1.4.1。修复对象来自此前冻结互联网样本测试，不根据某一份文档的实体数量编写答案；只输出本体类型、中文 name 和英文 code，人工审批与 OpenMind 身份约束继续保留。

## 1. 修复范围

- **B01 重复条款上传500**：来源单元 ID 加入文档内出现序号。同样的文字可复用内容缓存，但每次出现保留独立身份；重解析稳定、入库仍为事务。无数据库列或索引迁移。
- **B03 短段落放大模型请求**：同章节、同来源区域内的相邻正文合并为有界语义单元（4200字符/128个子单元），不跨明确标题、表格、原生对象、布局警告或业务记录边界。每个原始片段保留精确字符区间、位置和顺序；引文可回到原始出现位置。没有按文件名或特定章节号处理。
- **B02 多义词误判**：规则不再把设备/网络系统的“报警”自动解释为向警方报警。缺少动作主体和上下文时进入语义理解/协商；模型的窄化含义仍受来源约束。
- **B06 条件付款方式**：备选、计划或条件性转账不再默认生成发生事实的事件线索；仍保留原文，让实际模型和用户按主题决定是否纳入。法律声明中的“申明”不再误认成人名。
- **B05 未理解却完整缓存**：任何尚有语义文本、但未配置/调用模型的单元标为 `awaiting_model`，不能放入成功解释缓存。原文证据缓存仍可复用；配置模型后可继续。`processed` 仅表示处理经过，不是语义准确率或人工审批通过。
- **B04 PDF空打开口令**：允许对空口令可打开的PDF只读提取，不修改权限和文件；真实口令未知仍拒绝，不猜口令。
- **格式审计遗留问题**：Strict DOCX 在内存中做结构命名空间兼容，保持正文/表格顺序，原始文件不变。损坏索引PDF可由有超时限制的 Poppler 只读降级；标准表单保存值/按钮状态单独提取，XFA/签名/图形边界明确提示。

## 2. 阅读边界

不提供自动OCR，不声称还原任意图像、图表或复杂表格语义；旧二进制DOC仍需额外转换。语义窗口按字符预算，不冒充精确模型token预算。相邻正文没有可靠章节标记时不凭视觉猜测所属类型，范围由语义理解与人工协商确定。

公众业务原文、第三方模型权重、凭据及运行数据库均不随源码提交。原始样本在测试时按旧清单SHA256校验，原始字节未重写；报告同时记录可读、部分读取与拒绝项。

## 4. 升级

从v1.4.1升级没有新增数据库结构；需重新构建以安装poppler-utils。保留原 `.env`、数据卷、上传资料和已经审核的本体。建议升级前先备份PG。不要重新初始化配置，不要 `down -v`。

```bash
# 在原工程目录，先停止应用/worker、覆盖新版源码（排除.env/data/uploads）
docker compose stop ontology worker
docker compose up -d --build --no-deps --force-recreate ontology worker
curl -fsS http://127.0.0.1:8001/api/health
```

预期版本1.4.2-demo。旧HTML/Word/PDF必须重新解析原始文件，才能使用新的来源定位和语义分块；重新核对主题后再生成候选。旧审核结果不自动修改。新的解析/建议缓存版本与旧结果隔离。

`LLM_REQUEST_TIMEOUT_SECONDS`可通过原env_file配置，默认120秒，范围15–900；这是模型HTTP等待上限，不是文档完成时间承诺，也不是隐藏超时错误。
